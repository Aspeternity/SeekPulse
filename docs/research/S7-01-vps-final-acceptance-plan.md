## 3. 现场前必须通过的技术预检（尚未执行）

1. **运行形态**：确认单 Python 主进程、唯一 Telegram Session 所有者、单 SourceSupervisor、单 S2/S4 队列消费者和 Web 单 Worker；停机顺序与超时清晰，异常启动不会产生两份消费者。当前未满足（B01）。
2. **镜像与依赖**：镜像必须确实包含经过审查的 S3–S5 固定版本依赖、静态资源和应用入口；容器非 root、无 Docker Socket、回环 Web 不暴露公网。当前原 Dockerfile 不包含可选依赖，不满足。
3. **首次启动/旧数据**：旧 \`FeedPoller\` 与新 S3/S2 不能同时对同一目标发消息；现有 DB 的用户/目标/关键词需有版本迁移/兼容和完整的回滚设计。初始 RSS/TG 基线不补发历史；只有确实观测到的新增帖子可进入 S2 任务。
4. **目标身份**：Bark 与 ntfy 必须有独立可信的注册及安全存储方式，不把设备 key/URL 写入普通 SQLite、Issue、PR 或日志，不允许用户任意提交请求地址；每目标独立状态及退避。
5. **数据保护**：S6 在线 SQLite 快照须采用官方 Backup API、验证 manifest SHA-256、integrity_check/FK/schema。备份自身**未加密**，不能上传 GitHub/AI/日志。单独持有的 Telethon Session、.env、Bot Token 不在 SQLite 备份中，必须单独经审批保护。
6. **网络与身份**：测试 Telegram 会话、Bot 收件人、Bark/ntfy 接收端必须由用户授权，先核实后发第一条。网络不支持时记录 \`BLOCKED\`，不能以假客户端通过代替真链路。
7. **风险退出**：每个灰度子阶段前获得明确撤回/停机路径、快照和已知旧状态；若出现未知重复发送、凭据泄漏、DB 异常或未授权目标，立即暂停测试并报告用户，绝不自动恢复或跨越门槛。

## 4. 48–72 小时观测设计（只设计，不执行）

**计时开始条件：** G-B/G-C/G-D 均通过各自授权与验收；观测主机稳定地运行被批准的**完整 V1.1**链路，记录版本、Git SHA、测试开始/结束的 UTC 时间及允许中断规则。只有旧 Bot 在跑或凭据不可用时必须记录 \`NOT_STARTED\`。

- 建议资源采样每 **60 秒**：CPU 使用率/峰值、RSS 内存/峰值、Swap/OOM、磁盘可用容量/数据库及 WAL 字节数、容器重启次数、主机时钟/NTP 状态；事件级日志记录全部来源异常与发送状态，**仅存脱敏统计**。监测工具也需按低配 VPS 资源预算审批，避免自身耗尽 1 GiB 内存。
- 建议每 **5 分钟** 汇总两个来源独立的启停、最后成功时间、故障/429/Retry-After、持久 gap、游标推进（只能保留脱敏/聚合），每目标待发送/重试/失败/已接受任务、最老队列年龄；附独立检查者记录的已知可访问样本帖子集合/时间窗。
- 时间段：\`T0–4h\` 最小灰度核对授权收件人、基线与重复；\`4–24h\` 常态观测；\`24–48h\` 覆盖日内变化与失效恢复；若遭明显中断/样本不足，**不假报 48h PASS**，经批准延长至 \`48–72h\` 并列明有效观察时长与中断。不能把原本的 24h/旧版 Bot 观测当成 48–72h 完成。
- **事件指标**：必须使用 UTC 时间、相同真实 VPS 时间源。记录 \`post_id\` 去标识后的稳定键与来源、source first observed 时刻、发送请求起点、Telegram/Bark/ntfy API 返回/错误码、任务持久 \`sent_at\` 时间，及目标渠道。不能把论坛发布时间与服务器观察时间混为一谈。
- **P50/P95 口径**：\`source_first_observed_at → notification_API_accepted_at\`，仅针对**确有成功回执且时间戳可信**的任务，报告 **每渠道**和合并样本的有效 \`n\`、异常/未发送/过期数量、窗口、网络条件。良好网络且无积压时 \`P95 ≤ 5 秒\` 是既有产品计划中的**工程目标**，未达标须给根因/样本，不能掩盖。不能以 API accepted 宣称手机实际响铃。
- **覆盖率口径**：外部独立采样确定的可见帖子集合为分母，记录 RSS/TG 各自观察数量、并集、新增帖子/有效可匹配帖子、源不含帖子及未知原因；没有可信分母只写 \`UNKNOWN\`，不能编造 100%。对两来源同帖 \`(user,post,target)\` 必须只有一条常规持久任务；多规则不叠加普通通知，不同目标状态独立。
- **性能**：目标 VPS 为 1 vCPU / 1 GiB，报告实际 CPU 峰值/均值、RSS/Swap/OOM、磁盘和 WAL 的变化、启动时间/采集延迟/恢复时间；当前没有已获批准的额外硬阈值，不能临时宣称某 CPU 数字就是用户确认的验收线。任何 OOM、不受控重启、不可解释的数据丢失/超期/重复都判调查阻断。
- **安全/故障**：每次失败必须能关联受限错误码/时间和原因；429 按 Retry-After 等待，其他来源不能被饿死；Session 掉线期间不得越过游标，恢复后补查有界；数据库损坏/空间不足不能继续发错目标或丢审计。高风险注入只在 G-F **另外获批**后实施。
- **真实手机到达**：若用户批准，可在独立手动检查表记录通知收到与否/人工时间；不得并入 API 延迟 P95，也不能据单次人工体验声称端到端有保证。

## 5. 退出判定及停测原则

- \`PASS\`：明确受验 SHA 与环境、各 Gate 授权证明齐全；48h 以上有效 V1.1 全链路运行、必要的双源/多渠道测试证据、可解释的数据缺口、归属与去重审计、可审计恢复、真实资源报告、第二 AI 独立交接报告；用户明确最终验收通过。
- \`FAIL\`：已执行并出现实测功能/可靠性违约，保留脱敏故障证据、精确环境/版本和复现，不以重启清零抹掉。
- \`BLOCKED\`：集成入口/非 TG 目标/凭据/权限/测试 VPS 缺失，或没有经用户批准的实机方案；不给虚假的通过率。
- \`UNKNOWN\`：监测无覆盖、样本分母不明、缺时间戳或 GitHub/CI 不可查；不得把 \`UNKNOWN\` 改写成 \`PASS\`。
- **立即中止并征求用户指示**：Token/Session/密钥可能泄漏、发往未授权接收者、重复发送风险异常、备份/DB 不完整、生产访问控制改变或 host 不符合预期。不能自动删除数据、清理 WAL、重新部署或切换主库。
