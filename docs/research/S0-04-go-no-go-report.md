- 关联：[S0-04 #8](https://github.com/Aspeternity/SeekPulse/issues/8)、[S0-01 #5](https://github.com/Aspeternity/SeekPulse/issues/5)、[S0-02 #6](https://github.com/Aspeternity/SeekPulse/issues/6)、[S0-03 #7](https://github.com/Aspeternity/SeekPulse/issues/7)。
- 日期：2026-10-14。**仅为交用户审批的建议稿，不是已批准的最终架构决定。**
- 产品基线：[PLAN](../PLAN.md) 与 [ARCHITECTURE](../ARCHITECTURE.md) 已批准 V1.1 RSS + TG 两个独立来源及分别启停能力；本研究报告不擅自删掉 TG 或调整生产轮询设置。
- 研究授权只允许报告与非生产探针，不得开始 S1–S7、合并 PR、发布、修改生产或要求分享 TG 凭据/Session。

## 一、建议结论

**建议条件式 Go 进入 S1 上游基线研究开发（须用户单独批准）；保留已批准的双来源产品范围，不把“TG 比原版默认 10s RSS 快”视为已证实。**

- 已证实可行：官方频道真实 Telethon 回调、历史补查及停机后恢复；RSS 实际拉取；Apprise 2.0.1 Bark 和 ntfy 的本机回环接口及错误语义。
- 尚无充分证据：稳定网络下 TG 相对 RSS 10s 的净速度优势、独立漏报覆盖收益、真正手机/APNs 送达、正式 1vCPU/1GiB 全栈资源和通知 API 端到端时延。
- 不可宣称：RSS 10s 永久允许高频访问；TG 绝对更快；一方长期总是覆盖更多帖子；传输成功等于手机提醒到达。
- 待用户决定的变更：若要取消 V1.1 已批准的 TG 来源，只保留 RSS，必须通过单独产品范围变更与 ADR 明确批准。

### 网络干扰和测量边界

用户明确记不清 3 小时内修改网络的具体时间，因此**不做事后臆造的清洗或无依据异常样本删除**。目前的 10 秒 P95 可以表示这批受干扰时段中的极端延迟，不能表示 RSS 来源在稳定网络下固有 23 分钟延迟。10 秒和 60 秒来自不同时段，发帖率、RSS 缓存、网络路径、恢复窗口皆有混杂，不能用二者 P50 的差直接计算轮询提速因果效果。探针测的是**同机第一次观察到来源**，不是论坛发布时间、真正 API 推送完成或手机响铃。

## 三、架构选项与建议

| 选项 | 收益 | 代价与风险 | 与已批准 V1.1 的关系 |
|---|---|---|---|
| **A（推荐）：保留 RSS + TG 两来源，且可分别启停** | RSS 保持基础采集路径；TG 提供额外事件来源和历史补查机会；后到的数据补字段，同帖子唯一 ID 去重；单源故障应不阻断另一源 | TG 普通账号/Session 安全和维护负担；无法承诺更快或更全；真实可靠性须在 S3/S6/S7 证明 | 与 V1.1 产品范围一致，不强制两个来源同时开启；不在此改变正式默认启停状态或轮询频率 |
| **B：把 V1.1 改成 RSS-only** | 部署、权限与维护更简单，不需要 TG Session | 失去第二来源与补查路径；RSS 断网/feed 滚动时恢复手段受限；未必更快或更全 | 属于已批准产品范围变更，需要用户单独确认并形成 ADR |

**不建议**未经证实就要求 TG 永久常开，也不建议以研究脚本的 10 秒试验代替正式 RSS 频率限流与运营策略。

## 四、下一阶段控制与验收

1. **S1（需要用户批准）**：先建既有 AI-XMLY RSS、OR/AND 组合匹配、屏蔽词、栏目、多用户和多通知目标等上游回归测试，核验依赖版本和 CI；不需要再等 24 小时采样，也不要求先合并 #17/#18/#19。详见 [S1 #9](https://github.com/Aspeternity/SeekPulse/issues/9)。
2. **S2（仍未授权）**：按帖子真实 ID 唯一化、来源字段不完整不绕过栏目/屏蔽规则、SQLite 每用户/帖子/目标独立去重与任务租约；用自动回归证明并发和重启行为。
3. **S3（仍未授权）**：在获批的双源设计下分别控制 TG/RSS 生命周期；TG 会话互斥/重新连接/补查游标，RSS 超时/403/429 合规退避、20 条 feed 窗口溢出监测；以可检验指标评价 TG 是否带来独立收益。
4. **S4–S5（仍未授权）**：推送目标独立发送/重试，Bark/ntfy 受限适配、禁任意 URL SSRF，Web/Bot 业务配置一致、权限与安全；不把通知 API 成功当作手机已收到。
5. **S6–S7（仍未授权）**：真实 VPS 全栈 1vCPU/1GiB、长时资源、网络/Session 故障注入、备份恢复、48–72h 非生产实机与真实通知终点验证，单独申请合并/发布批准。

## 五、用户需批准的决策

请分别确认：(a) 是否接受 **S0-04 条件式 Go：保留双来源能力但不宣称 TG 的 10 秒时效优势**；(b) 是否**单独授权实施 S1 / Issue #9** 的上游行为回归与 CI 基线。该批准不包括 S2–S7、PR 合并、版本发布、生产变更。

在明确收到用户同意之前，**本报告仍为待验收建议**，S1 仍为待授权；这份 Markdown 的 CI 成功只能证明文档与工程检查合格，不能代替用户验收或真实网络功能验证。
