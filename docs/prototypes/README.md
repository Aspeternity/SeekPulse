# SeekPulse Web-first A 阶段原型（V2）

> **产品设计原型，不是已经部署的 SeekPulse。** 对应 Issue #59 / Draft PR #60。此目录与正式运行的 `app/`、Compose、Docker 镜像、数据库和通知协议隔离。

## 启动与体验

下载 `seekpulse-web-first.html`，使用 Edge / Chrome 直接打开，不需要 Docker 或网络。**请勿输入真实密码、Token、手机号、Session、API Hash 或设备 Key。**

第一次打开时，展示**独立的创建管理员账号页面**；输入虚构的用户名和至少八位演示密码，两次一致后切换到**独立登录页面**。用同一用户名和任意八位演示密码即可进入 Web 主界面。原型**不会存储或校验真实密码**，所以刷新后重新展示注册，不能当成真实身份认证或生产安装。

登录后的六页面：

| 页面 | 原型表现 |
|---|---|
| 运行概览 | 来源运行模式、可选通知渠道、运行活动和示例统计 |
| 监控来源 | RSS/TG 独立启停；TG 授权与启用分离；四种来源组合模式 |
| 关键词规则 | 新增/修改/暂停/删除、AND 组合、屏蔽词和通知目标覆盖 |
| 通知管理 | Telegram Bot、Bark、ntfy 各自配置；Bot 启停/命令入口；目标和路由 |
| 推送历史 | 按目标/状态查看演示结果、错误和重试信息 |
| 系统设置 | 管理员、会话、备份、诊断与主题入口（仅模拟） |

### 确定的架构原则

1. **Web-first**：Portainer/Compose 仅管镜像、端口、数据持久化；Web 独立提供首次注册/后续登录和配置管理。用户注册不绑定 Telegram Bot；不设置强制五步首次向导。
2. **采集引擎独立**：RSS、TG 分别启停；仅 RSS、仅 TG、同时运行、两者停止均是合法状态。TG 来源需先授权普通 Telegram 账号，账号授权成功与来源启动是两个动作。
3. **同一套业务算法**：统一 NodeSeek 帖子 ID、规则匹配、持久化去重、按目标投递及重启恢复应在所有采集模式存在。RSS+TG 同时运行时，再利用跨来源合并、字段补全、缺口补查；TG-only 不能虚构 RSS 的版块/摘要。
4. **通知引擎独立**：Telegram Bot、Bark、ntfy 为可选通知能力；只选 Bark 或 ntfy 时，不需要配置 Bot。启用 Telegram Bot 后，**通知发送与 Telegram 命令管理都可使用**，例如 `/start`、`/keywords`、`/combo`、`/pause`、`/resume`；Bot 命令与 Web 读写同一业务配置，不能形成第二套规则。
5. **TG 频道来源不是 Bot**：使用普通 Telegram 账号（Telethon）读取 `@nodeseekc`；启停 Bot 不应启停 TG 来源，反之亦然。
6. **运行管理器负责启停和状态**：业务组件未配置、授权失效或单个模块异常，不应使 Web 无法访问。配置修改由 Web 后端统一验证、持久化与应用；原型只模拟按钮。
7. **持久化与恢复**：正式版须区分新安装和旧数据损坏，不能无提示重建旧数据库；敏感配置不应要求频繁编辑 Compose，管理界面只展示脱敏状态。

## 原型测试范围与限制

- 该 HTML 文件自包含 CSS/JS，不使用 CDN，不请求 NodeSeek/Telegram/Bark/ntfy，所有按钮均为离线交互模拟，不操作真实 NAS/PVE/Portainer 或数据库。
- A 阶段目标是**先验收界面架构和使用流程**，不是声称后台已经支持 Web-first。管理员认证和一次性首装授权、网络访问、持久化密钥、TG Session、Bot 命令与 Web 数据一致性、组件生命周期等均在 B/C 阶段单独设计和验证。
- V2 用户重点验收：**注册→登录→概览**、四种 RSS/TG 模式、Bot 命令/通知共存、Bark/ntfy 无需 Bot 的独立使用、规则/历史/设置入口以及移动端布局。
- 需要用户明确的 A 阶段验收、独立 PR 合并授权；**当前不修改 main、不启动 B 阶段后端实现、不发布 RC2/Stable。**

后续阶段：B 最小 Portainer 单 Compose + Web/管理员/首装；C RSS/TG/三种通知真实 Web 配置和可控启停；D 规则历史备份诊断闭环；E 真实 NAS/PVE/Portainer 长期运行、升级/回滚与发行验收。
