# SeekPulse V1.1 — 已批准的产品和工程基线

- **方案批准日期**：2026-10-13。**最新阶段授权截至 2026-10-14 为 S2 / Issues #10、#11**，详见 [`APPROVALS.md`](APPROVALS.md)；产品范围不因授权阶段变化而改变。
- **项目目标**：以 NodeSeek 新帖为对象，提供双来源低延迟发现、关键词规则、多渠道通知和 Web 管理，同时保持轻量及可靠运行。
- **项目定位**：单机 Docker 自部署的开源工具；适配低配 VPS；保留原版有价值的 Telegram Bot 多用户能力；不建设 SaaS。

## 一、需要交付的用户功能

1. **两个独立来源**：NodeSeek 官方 RSS (`https://rss.nodeseek.com/`) 与其 Telegram 频道 `@nodeseekc`。先发现者先处理，各自独立重试与健康监测。TG 使用专用普通 Telegram 账号+Telethon，不是 Bot Token。初次启动不补推旧帖，重启/故障恢复必须补查可恢复的范围。
2. **统一帖子实体**：可靠地提取 NodeSeek 帖子 ID、规范化 URL，记录 TG/RSS 的首次发现时间和字段来源。不能根据类似标题猜测 ID；后到数据只补全，不重复通知。
3. **关键词**：普通词、OR、AND 组合、屏蔽词、版块过滤、标题或可用摘要匹配、启停。未获取足够条件所需字段时等待补充，不能擅自忽略版块过滤。普通用户能简单使用，高级设置按需展开。
4. **通知**：Telegram Bot 原生推送；Bark 和 ntfy 通过受限 Apprise 适配。每个用户可配置全局默认通知目标和规则级覆盖。单目标和并行通知正式支持；复杂的失败备用不进入首版。
5. **优先级**：普通/紧急两级。都尽快通知；紧急任务优先使用有限 Worker 容量，必须遵守平台限流；不同目标并行、独立计时及失败重试，普通任务不得长期饥饿。
6. **可靠投递**：每用户+帖子+目标只创建一条常规持久化任务；SQLite 原子去重、短事务、任务租约、有界重试和独立投递状态；已成功的目标不因另一个目标失败而重发。承认极端崩溃窗口可能引起重复，不承诺严格 Exactly Once。
7. **Web**：FastAPI + Jinja2 + HTMX（本地静态资源），现代简洁中文界面，移动适配及明暗主题；仪表盘、关键词、来源、通知渠道、推送历史、统计、设置。Web/TG 命令共用业务服务与数据库。
8. **权限**：默认仅管理员 Web 登录和 Bot 白名单；保留原 Bot 多用户的数据隔离，不为非管理员用户提供 Web 登录。Web 默认回环地址访问，建议 SSH 隧道或可信私有网络。
9. **运行与运维**：一个 Python 主进程、一个 Web Worker、一个采集实例、单 Docker Compose；SQLite WAL；非 root 容器、无 Docker Socket；凭证与 Session 不入日志/代码；受控备份、迁移、升级/回滚；不自动部署发布。
10. **可观察性**：来源最后正常时间、TG/RSS 首次观察时间、每目标投递结果、队列深度/最老任务等待时间、错误状态、数据缺口、P50/P95 延迟。区分论坛→来源、来源→通知 API、API→手机这三段，不能将 API 成功当作手机已响铃。

## 二、架构硬约束

- **模块化单体**：Sources → Normalizer → Posts → Rule Engine → Router → SQLite Delivery Queue → Notifiers；首版不做动态插件市场、微服务或分布式队列。
- **静态适配器**：允许后续扩充来源和通知通道，但不执行用户上传的第三方代码。
- **配置唯一**：普通业务配置保存在 SQLite；部署秘密按受保护文件/环境变量管理；Web 和 Bot 不建立第二套业务配置。
- **源字段有限**：来源给出的标题/摘要可能不完整；屏蔽词不能声称检查了根本没拿到的正文。
- **任务过期**：首版以 30 分钟为候选默认时效窗口，S0/S6 实测后确认；超期保留 `expired` 审计记录并优先处理新鲜消息，不静默删除。
- **许可**：在 AI-XMLY 的 MIT 代码和历史上迭代；参考 GPLv3 项目设计但不直接复制实现。

## 三、不进入首版的内容

直接抓取受保护论坛页面；自动购买 VPS/支付；任意网站/频道爬虫；AI 自动判断价格与紧急程度；复杂正则表达式平台；任意 URL Webhook；公开 SaaS 和完整多租户 Web；React/Node 独立运行服务；Redis/PostgreSQL/分布式队列；动态执行第三方插件；无人值守升级、自动合并及自动发布。

## 五、首版质量验收

- 双来源可分别开启/关闭且独立运行；任何一方异常不使另一方停止。
- 同帖跨源、同帖多规则和重复消息输入，同一目标仅创建一次常规通知任务；独立目标有独立状态。
- 未知版块/不完整字段不绕过过滤；来源字段补全遵守预定规则。
- 故障恢复后队列任务可继续，限流和不可恢复失败有记录；确认 Telegram Bot API 非严格 Exactly Once 边界。
- Web 和 Bot 改动配置即时一致，管理员和普通 Bot 用户数据隔离。
- Docker 容器重启、TG Session 失效、RSS 超时、平台发送失败及数据库恢复均经自动/实机测试。
- 使用 1 vCPU / 1 GiB RAM 进行真实资源测试；首次发现到 API 接受在良好网络与无积压条件下以 P95 ≤5s 为**工程目标**而非承诺；论坛发帖到手机响铃不在可保证范围。
- 每个 PR 关联 Issue、提交 SHA、测试、风险、回滚；最终最新 SHA 的完整 CI 全绿、用户实机验收明确通过、独立批准合并及发布。
