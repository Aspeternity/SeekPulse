## 1. 交付方式与不可绕过的闸门

- 旧 `Dockerfile` / `docker-compose.yml` / `requirements.txt` 继续保留原 RSS Bot，**不会**悄悄升级旧容器。新 `Dockerfile.v11` 使用 Python 3.11 + `requirements-s5.txt` 完整固定依赖 + Web 模板/静态资源，默认非 root 10001:10001，入口 `python -m app.v11_main --run`。
- `compose.v11.yaml` 只使用 `SEEKPULSE_IMAGE` 指定的、未来独立批准的镜像引用（建议 GHCR `@sha256:` digest）；不会让 PVE/群晖用户本地 build。可作为未来 Linux Docker Engine Standalone 的 Portainer Stack 或群晖 Container Manager Compose 输入，**尚未实际在二者测试**；Swarm 不在此范围。
- `SEEKPULSE_V11_ENABLE=1` 和明确的 `--run` 是代码级要求。**数据库还必须先由管理员独立初始化并 Prime**；`docker compose up` 自身不会建库、迁移、Prime、发历史帖、生成 Telegram Session。未准备完成时启动入口会拒绝。
- 默认 `restart: "no"`，未完成真实灰度许可前不会失败重启风暴；生产自动重启策略单独审查。

## 2. 数据目录、配置与密钥

- 在实际获准部署时先建立单独、**空的、绝对路径**私有数据目录，例如 Linux Docker Host 上 `/opt/docker/seekpulse/data`，或群晖上适合容器挂载的 `/volume1/docker/seekpulse/data`。填入 `SEEKPULSE_DATA_DIR`，与容器内 `/app/data` bind，`create_host_path: false` 阻止拼错路径被自动创建。
- 非 root 镜像 UID/GID 默认 `10001:10001`，数据目录必须允许该 UID/GID 写入；可通过 `SEEKPULSE_UID/GID` 匹配未来宿主授权 UID，但不能为了排错随意运行 root。数据库、WAL/SHM、`bot.db.owner.lock`、日后批准使用的 Telegram `.session` 均保存在持久卷；不可误将其置于只读镜像层。
- `.env.v11.example` 只有假占位符，填好后放在受保护的位置，**不得上传 GitHub/PR/Issue/AI**。必填环境：`SEEKPULSE_IMAGE`、`SEEKPULSE_DATA_DIR`、`BOT_TOKEN`、`ALLOWED_USER_IDS`、`SEEKPULSE_ADMIN_TG_USER_ID`、`SEEKPULSE_WEB_PASSWORD_HASH`。Portainer/群晖管理员与 Docker Host 管理员可能通过其权限查看容器环境变量，不能把 Compose 环境本身当成硬件密钥库。
- Web 密码至少 12 字符，采用可信本地终端运行 `python -m app.web_auth` 生成的 scrypt 哈希；不要把明文放在 shell 参数或项目文件中。Bark/ntfy 目标对应 `SEEKPULSE_PUSH_<REF>` 私有环境值，数据库中只记录安全引用，必须由管理员明确启用，限制官方 HTTPS；不在本阶段使用任何真实设备信息。
- TG 来源**默认关闭**；后续如要启用 Telegram 频道读取，需显式配置全部 `SEEKPULSE_TG_API_ID`、`SEEKPULSE_TG_API_HASH`、`SEEKPULSE_TG_SESSION`（已授权现有 `.session` 的绝对路径），不能自动登录或重新生成 Session。

## 3. 全新独立安装：将来的显式三段操作（Docker-02）

**仅适用于完全空的新数据目录。以下是未来真实部署批准后的人工作业示例，目前不得执行到真实 PVE/NAS。**

1. **先配置 Compose 环境与存储权限。** 受保护的本地 `.env` 可来自 `.env.v11.example`，管理员须事先填好必需变量、选择未来已批准发布的镜像 digest；这一步不意味着运行容器。
2. **仅一次离线建库/Prime，绝不发送通知**：在获授权限的 Linux Docker 命令行或等效的、独立批准的 Portainer 一次性任务中执行：
   ```bash
   docker compose --env-file .env -f compose.v11.yaml run --rm \
     -e SEEKPULSE_FRESH_INIT_CONFIRM=CREATE_EMPTY_DATABASE \
     seekpulse --init-fresh
   ```
   `--init-fresh` 仅接受`SEEKPULSE_V11_ENABLE=1`、确认标志和`DATABASE_PATH` 为**绝对路径**、数据目录已存在且为空（允许本实例的 `.owner.lock`），且目标 DB / `-wal/-shm/-journal` 均不存在。先在私有随机 staging DB 上建完整业务表、目标 schema、显式零高水位 Prime、S6 完整性核验，再以**禁止覆写的原子 hardlink**发布。即使重新执行，也必须拒绝覆盖既有数据。目录内若已有 Session、其他 DB、备份、旧文件，同样拒绝；应先人工核对目录选择，**不能删除文件来强行通过**。
3. **只读核实准备状态**：
   ```bash
   docker compose --env-file .env -f compose.v11.yaml run --rm \
     seekpulse --check
   ```
   返回 `v11_database_ready` 仅证明已有 Gate B schema + Prime 游标，**不保证网络、Webhook、Token、Web 或手机通知成功**。
4. **单独批准后方可运行真实服务**：
   ```bash
   docker compose --env-file .env -f compose.v11.yaml up -d
   ```
   此命令会启动 Bot/RSS/Web/Worker，**真实执行必须属于未来 Gate D 的独立授权**；如数据库未备妥会拒绝，绝不可添加自动修复或 Prime 作为绕行。

**Portainer GUI 备注**：Stack 的普通 `up` 不等于上述一次性 init。未来可由管理员创建与该 Stack **同镜像/持久卷/UID/环境**的一次性 `--init-fresh` 容器任务，再 `--check`，最后部署正式 Stack；不能让旧容器和新容器同时读写 DB 或同时发送。群晖 Container Manager 也应遵守同样顺序。**Portainer/群晖 UI 操作和 Compose 方言尚未进行实机验收。**

## 4. 已存在数据库：仍走 Gate B / S6 备份迁移，不能使用 --init-fresh

- **只要检测到任何 DB、WAL、其他文件或有旧运行实例，就不要使用 `--init-fresh`**。已有实例必须先独立批准“停止旧镜像和来源、验证独占、执行 S6 在线/一致性备份、确认可恢复、原有 `--prepare` 安全迁移/Prime、校验、再运行”的 Gate D 流程。
- `--prepare` 对所有**已存在的旧库**仍要求经 S6 校验的 `SEEKPULSE_VERIFIED_BACKUP_BUNDLE`；新增全新空库命令**绝不代替旧库备份、回滚或迁移**。旧镜像可能不具备实例锁，停机不能只依赖 V1.1 lock；升级后不能把旧镜像指向迁移后的数据库。
- 首次使用 RSS 时沿用 S3 初始窗口不补发历史，TG 默认关闭；初次用户身份和 Telegram Bot `/start` 的真实配置将来独立验证。

## 5. Web 网络安全与 Docker 限制

- S5 管理 Web **同时校验 TCP 客户端为回环地址及 HTTP Host 合法**，拒绝 Forwarded/X-Forwarded。不允许通过删除检查、监听 `0.0.0.0` 或公开反向代理来“修复”无法访问。
- `compose.v11.yaml` 使用 **Linux `network_mode: host` 且没有端口映射**；Uvicorn 固定绑定宿主回环 `127.0.0.1:8765`（端口可配），不公开给 LAN。受授权管理员未来可通过可信 SSH 本地转发访问：`ssh -L 8765:127.0.0.1:8765 <user>@<docker-host>`。此设计使容器共享 Linux 宿主网络命名空间，必须在未来使用已有许多容器的 PVE/群晖前复核隔离、端口和版本兼容；不支持当前未验收的 Swarm/macOS 环境。
- 根文件系统只读、非 root、无 Docker Socket、drop ALL capabilities、no-new-privileges、私有数据卷；真实 CPU 架构 x64/ARM64 和硬链接文件系统兼容尚未知，CI 离线通过并不代表这些已实测。

## 8. Docker-04：基础镜像供应链、CVE 与 SBOM 离线审查（不发布）

- **基础镜像固定**：`Dockerfile.v11` 的 `FROM` 已固定在官方 `python:3.11-slim@sha256:e88e9763f943ec1834f992a4b51e0f24500486803e8bc534e5767af9ea65f6ce` 多平台索引。2026-10-15 的只读 [GH Actions #38632803851](https://github.com/Aspeternity/SeekPulse/actions/runs/38632803851) 确认官方 Registry 该索引包含 `linux/amd64` 与 `linux/arm64`。这是**Python 基础镜像的 Digest**，绝非发布到 GHCR 的 SeekPulse 镜像 Digest；基础镜像安全升级必须对新候选重新审查和双平台回归。
- **扫描范围**：仅 GitHub 临时 runner 中的本地 AMD64 与 ARM64 V1.1 镜像，以固定版本的 Trivy（依赖 GitHub Actions 中 SHA 固定的安装 action）扫描 Debian OS 包和实际 PyPI 包；同时生成各自 CycloneDX JSON SBOM。`scripts/v11_security_evidence.py` 验证扫描器 JSON、OS 与 Python 两类库存、DB 更新时间/下载时间、SBOM 时间、镜像 ID、平台与非 root 入口是否匹配。不能用无扫描数据、空 SBOM 或过期 CVE 数据库冒充完成。
- **扫描报告解释**：`LOCAL_SECURITY_EVIDENCE=VALID` 只证明一次扫描证据有效；只要有 **HIGH/CRITICAL** 就必须在 `vulnerability_gate` 明确 `BLOCKED_HIGH_OR_CRITICAL`，低中危也至少 `REVIEW_REQUIRED_NONBLOCKING`，scanner/数据库不可用则 `UNKNOWN`（CI 失败）。**所有本地扫描的 `release_authorized`、`release_ready` 均始终 `false`。** 即使 CVE 为零，也必须接受人工供应链审查和单独发布授权，才能在未来正式发布。

## 9. Docker-05：高危漏洞定向处置（仅离线开发、非正式发布）

- **基线问题**：Docker-04 2026-10-14 双架构 Trivy 公开 DB 中，每架构 High 共 48 条（OS 44、PyPI 4），去重 CVE 12 个；GHCR 发布闸门仍 `BLOCKED_HIGH_OR_CRITICAL`。High 计数是受影响包与漏洞的记录数，不代表独立漏洞数量或已经可以被外部利用。
- **本次修复的具体边界**：只在 `Dockerfile.v11` 内，在已有 `requirements-s5.txt` 之后**同一安装层**执行 `pip install --upgrade -r requirements-v11-security.txt`，限定三个精确版本：`aiohttp==3.14.3`（修复两项已知 CVE）、`jaraco.context==6.1.0`、`wheel==0.46.2`；同层运行 `pip check`。**旧版 `requirements.txt`/S3/S4/S5 和默认 Dockerfile/Compose 不受影响**，旧容器也不因此自动获得修复。
